## 3. 训练脚本 v2（scripts/train_sft_v2.py）

旧 `train_sft.py` 吃旧的 `{"image","question","answer"}` 单行格式，且 LoRA 配置是旧配方（r=16 只加 q/v_proj），与 docs/13 冲突。新脚本：

- **数据格式**：吃 delivery_v02 的 messages 格式，`<图片占位>` 换成图片块，图片只插第一条 user 消息；支持多轮（guide 两轮）。
- **LoRA 配方（docs/13）**：语言侧全部线性层 q/k/v/o_proj + gate/up/down_proj，rank 32 / alpha 64 / dropout 0；视觉编码器和 merger 冻结；lr 2e-4 恒定（warmup 3%）；有效批次 32（8×4）；bf16；3 epoch。
- **多轮 loss**：逐 assistant 轮定位 token 区间，只在这些 token 上算 loss；tokenize 结果缓存到磁盘（多轮样本要跑 4~5 遍 processor，不缓存每个 epoch 都要重跑）。

### 掩码单元测试抓到的两个 bug（已修）

写脚本时的假设错误，用「loss 区解码回来必须等于金标答案」的单元测试抓住：

1. **前缀切片**：算某轮 loss 起点时用了 `blocks[:i+1]`，但单轮数据的 jsonl 里已带金标回答，会把答案拼进前缀。改成 `blocks[:i]`（该轮 assistant 之前的消息，以 user 结尾）。
2. **终点切片**：终点用了 `blocks[:i+2]`，多轮时会越过多吃下一轮 user 问题。改成 `blocks[:i+1]`。

修复后 6 种问法（direct/probe_seat/probe_feet/caption/chain/guide）全部通过：前缀 token 完全一致、loss 区解码与金标逐字一致、loss token 数合理（单词答案 3~4 个，caption/chain 约 140 个）。

## 4. 评测脚本 v2（scripts/eval_v2.py）

- 吃 `data/sft_v2/test.jsonl`（冻结，161 条，四种问法），逐样本逐轮生成，最后一轮计入指标。
- 每种问法用自己的判分：direct 看「推行/骑行」最后出现；probe_seat 期望 没有/有；probe_feet 期望 地上/踏板；caption 用关键词启发式判「有没有把推行说成骑行」，原始文本全量存档供人工复核。
- fp32 全程跑（A100 40GB 放得下 3B，避开 fp16 NaN 帧乱码问题，旧设备的坑见 HANDOVER §5）。
- 输出：分问法准确率 + direct 混淆矩阵 + 逐条预测 jsonl + summary json（进 `results/`）。
